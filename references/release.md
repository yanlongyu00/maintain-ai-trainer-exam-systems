## 发布前置门

收到用户“确认发布”后仍需先确认：

- 本次目标系统、正式 URL、Netlify 项目和妙搭 app_id；
- 权威源码哈希与待发布产物哈希；
- 回归报告没有阻断项；
- 已保留上一可用版本或可恢复发布包；
- 发布包不含截图中的个人信息、凭据、临时预览绕过代码；
- 同一包内未修改页面仍与线上基线一致。

## 发布责任矩阵

发布前用一句话逐项确认，不把“用户自己拖 Netlify”推断成“其他平台也由用户处理”：

| 平台 | 目标 | 操作者 | 完成证据 |
| --- | --- | --- | --- |
| Netlify | 准确项目名与正式 URL | 用户拖拽或助手操作，二选一 | Published 后下载线上 HTML 核对哈希 |
| 妙搭 | 既有 app_id 与备用 URL | 用户明确要求时由助手发布；否则写明本轮不更新 | `html-publish` 返回发布 URL，查询公开范围并下载验收 |

“预览可以”“就这样”“修改没问题”只确认预览，不自动授权发布。用户明确要求发布到某个平台后，不要重复确认同一动作；但未被点名的平台仍需说明是否同步。

## 预览交接

发布前报告必须包含已经验证可打开的本机预览链接。用户在预览阶段追加需求时，先更新权威源码和预览并重跑测试；不要直接把预览反馈补丁打进发布副本。

`127.0.0.1` 预览只对当前电脑有效。用户要在手机查看时先解释该限制；未经“确认发布”不得把 Netlify 或妙搭当作临时预览环境。

## Netlify

该项目历史上主要使用网页端拖拽部署，不要假设已安装 Netlify CLI。

### 理论与实操主站

目标站点：`<theory-and-hands-on-netlify-site>`

发布包根层级至少保持：

```text
index.html
hands-on.html
_redirects
```

如果现有线上包还包含 `venue.html` 或 `vendor/`，先确认其用途，再决定是否原样保留。修复单页不能让其他已售卖页面从部署包消失。

若当前线上包包含 `venue.html`，只更新理论页时：

1. 下载当前线上 `hands-on.html` 和 `venue.html`，或证明本地候选与线上哈希完全一致；
2. 仅用新理论源码替换根层级 `index.html`；
3. 保留 `_redirects`；
4. 打包前后列出文件名、大小和哈希，禁止用陈旧 `share.zip` 还原其他页面。

### 考场站

目标站点：`<venue-netlify-site>`

用户销售链接是 `/venue.html`，因此上传包必须实际提供 `venue.html`；若同时提供 `index.html`，验证两者的路由关系。Python 本地依赖存在时保留 `vendor/`，并在线检查文件请求成功。

### 考场确定性打包

优先运行 Skill 自带脚本，避免手工复制漏文件：

```bash
python3 scripts/build_venue_release.py \
  --source <已测试的venue.html> \
  --output-dir <新的空目录>
```

脚本固定生成：

```text
<output-dir>/
├── netlify/
│   ├── index.html
│   ├── venue.html
│   ├── _redirects
│   └── vendor/*.whl
├── miaoda/index.html
├── venue-netlify-<version>.zip
└── manifest.json
```

要求：

- `index.html`、`venue.html`、妙搭 `index.html` 与已测试源码哈希一致；
- ZIP 根层级直接包含页面、`_redirects` 和 `vendor/`，不得包含外层目录或 `venue-runtime-test.html`；
- 入口保留访问控制、版本标记、标准输出标签和运行结果差异说明；
- 脚本拒绝覆盖非空输出目录。需要重建时使用新的版本目录，不删除旧包。

### 网页部署

优先使用已登录的浏览器状态进入准确项目的 Deploys 页面。上传前展示 ZIP 文件列表，确认没有外层目录。上传后等待 Published，再重新下载或打开线上页面核对版本标记和关键功能。

不要误把另一个名称相似的 `-pro` 项目当作当前正式站。

用户有多个 Netlify 账号、登录身份不明确或明确表示自己拖拽时，不操作账号：

1. 生成并核验 `share.zip`；
2. 提供可点击的绝对文件路径、目标项目名和 ZIP 根层级清单；
3. 等待用户回复“上传完成”；
4. 再从正式 URL 下载线上文件并完成验收。

## 妙搭

妙搭静态站更新需使用 `lark-apps` 操作规范。首次操作前按其要求使用 user 身份和 apps 域授权。

发布前先测三项体积：单个 HTML 不超过 10MB、压缩后不超过 20MB、未压缩总量不超过 200MB。任一超限立即停止。

复用既有 app_id：

```bash
lark-cli apps +html-publish --app-id <app_id> --path <index.html-or-clean-dir> --dry-run --as user
lark-cli apps +html-publish --app-id <app_id> --path <index.html-or-clean-dir> --as user
```

单文件发布的文件名必须是 `index.html`。若权威源码不是该名称，复制到临时干净目录再发布，不要为了托管改坏源码命名。

理论妙搭产物允许且仅允许移除不蒜子外部脚本和 `busuanzi_container_site_uv` 容器。生成后把该差异归一化，再证明核心业务哈希与权威源码一致；不要把 Netlify 文件机械复制到妙搭，也不要让妙搭差异反向污染权威源码。

发布成功读取返回的 `data.url`，不能用开发态链接代替顾客访问链接。然后查询运行时可见范围：

```bash
lark-cli apps +access-scope-get --app-id <app_id> --as user
```

顾客入口通常需要 public 且不要求飞书登录；如果当前范围不符合，不要静默修改。向用户说明影响并获得确认，再按 `lark-apps` 规范设置。

`dry-run` 通过而正式发布遇到明确的瞬时网络错误（例如 EOF、连接重置、网关超时）时，可按完全相同参数重试一次，并告知用户正在重试。第二次仍失败就停止，不新建应用、不改 app_id、不反复重发。

## 线上验收

每个已发布入口至少检查：

1. HTTP/页面加载成功，标题与目标系统一致；
2. 访问控制符合产品设计；
3. 本次修复点在真实线上可复现为正确结果；
4. 控制台没有新的脚本错误；
5. 关键依赖请求无失败；
6. 刷新后状态恢复正常；
7. 手机或电脑目标设备关键路径正常；
8. 正式站和备用站的业务版本一致；
9. 旧缓存场景有明确刷新办法。
10. 发布责任矩阵中的每个平台都有完成证据；未发布的平台明确标为未更新，不能用“已发布”笼统带过。

验收时优先使用带版本参数的 URL 绕过旧缓存，例如 `?v=<APP_VERSION>`。分别下载线上 HTML：正式站应与 Netlify 产物哈希一致；妙搭应与妙搭产物哈希一致。若浏览器环境对 `aiforce.cloud` 报网络策略错误，但直接 HTTP 下载成功，不要误判为发布失败；对下载到的真实线上 HTML 运行相同回归测试，并把浏览器交互写为未验证或改用用户可访问的浏览器复核。

只验证本地文件不能宣称“线上已验证”。

## 回滚

发布前保存上一可用包的路径、哈希或 Netlify deploy 标识。若线上验收失败：

1. 停止继续更新另一个平台；
2. 优先恢复上一可用版本；
3. 验证恢复后的入口；
4. 告知用户失败原因、影响时间和下一步；
5. 不用清除顾客数据作为回滚手段。
