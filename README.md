# 人工智能训练师备考系统维护 Skill

这是一个面向“已售卖网页产品”的系统维护 Skill。它把零散的顾客反馈，转化为一套可追溯的处理流程：确认系统与版本基线、复现问题、诊断根因、实施最小修复、执行回归测试、提供本机预览，并在用户明确确认后完成双平台发布与线上验收。

> 本仓库是公开脱敏版。真实生产网址、平台应用 ID、历史任务编号和本机绝对路径均已移除；完整私有版本仍保留在本地。

## 为什么做这个 Skill

我维护三套人工智能训练师三级备考网页系统：理论刷题、实操训练和电脑端考场还原。顾客反馈经常跨越题库、判分、浏览器存储、手机布局、Python 运行环境、CDN、缓存和多平台版本一致性等问题。

如果每次都从头判断，很容易出现四类风险：改错版本、修一个页面影响另一个页面、用清空进度掩盖数据问题，以及把“预览确认”误当成“同意发布”。因此我把实际维护经验、故障案例、验收标准和发布门禁整理成这个 Skill。

## 它能做什么

- 从截图、顾客描述和链接中提取可复现条件与影响范围；
- 比较源码、发布副本、历史包和线上页面，建立版本基线；
- 诊断题目身份、判分、状态持久化、布局、依赖和托管线路问题；
- 保护题库、访问控制、浏览器进度和同一部署包中的其他页面；
- 执行正确路径、错误路径、刷新恢复、慢网、断网、窄屏和旧数据回归；
- 先提供本机预览，只有收到“确认发布”后才修改线上状态；
- 对 Netlify 与妙搭分别记录操作者、产物、状态和验收证据；
- 生成可以直接回复顾客的话术和发布报告。

## 核心工作流

```text
顾客反馈
  ↓
确认系统、入口、复现步骤和影响范围
  ↓
建立版本基线 → 诊断根因 → 给出最小方案
  ↓
等待“确认修改”
  ↓
最小修复 → 回归测试 → 三遍审查
  ↓
本机预览
  ↓
等待“确认发布”
  ↓
双平台发布 → 线上验收 → 顾客回复
```

最重要的两道门禁是：**确认修改**和**确认发布**。诊断、预览与上线是三种不同状态，不能互相替代。

## 仓库结构

```text
.
├── SKILL.md                         # 触发条件、原则和完整工作流
├── agents/openai.yaml               # 在 Codex 中展示的名称与默认提示
├── references/
│   ├── systems.md                   # 系统地图、版本基线与产品不变量
│   ├── diagnosis-and-tests.md       # 诊断方法与回归测试矩阵
│   ├── release.md                   # 预览、打包、发布和回滚规范
│   └── cases.md                     # 从真实故障中提炼的可复用规则
└── scripts/
    ├── preflight.py                 # 只读比较候选文件、哈希和关键标记
    └── build_venue_release.py       # 生成可复核的确定性发布产物
```

## 使用前配置

1. 把仓库目录放入 Codex 的 skills 目录，或让 Codex 从当前目录读取该 Skill。
2. 在 `references/systems.md` 中填写自己的正式入口、备用入口、项目名和应用 ID；不要提交访问码、令牌或后台凭据。
3. 按自己的项目目录调整 `scripts/preflight.py` 中的候选相对路径，或运行时显式传入资料目录。
4. 如果需要发布到妙搭，另外安装并授权 `lark-apps`；只做诊断和本地测试时不需要。

只读预检示例：

```bash
python3 scripts/preflight.py \
  --system all \
  --materials-root /path/to/current-materials \
  --legacy-root /path/to/legacy-project
```

考场发布包示例：

```bash
python3 scripts/build_venue_release.py \
  --source /path/to/tested-venue.html \
  --output-dir /path/to/new-empty-output
```

## 触发示例

- “顾客反馈错题本里不是自己的题，先检查原因。”
- “实操系统手机展开后有一大段空白，做个预览。”
- “代码题一直运行中，修好后做第一性原理和对抗式审查。”
- “确认修改，回归没问题后再给我打包。”
- “确认发布到 Netlify 和妙搭，并检查两个链接。”

## 这个 Skill 的原创性

它来自我持续维护真实付费产品的经历，不是把通用开发提示词重新包装。核心差异在于：

- 把顾客语言映射为题目身份、状态机、浏览器存储、判分契约和托管差异；
- 把“保护已售卖产品”设为高于顺手重构的约束；
- 把历史故障写回测试矩阵，让同类问题不再重复发生；
- 把版本基线、预览门禁、发布责任矩阵和双平台验收串成一个可执行闭环。

## 边界

- 用户只要求检查或讨论时，不修改文件、不发布；
- 证据不足时不把推测写成根因；
- 不通过清空 `localStorage` 掩盖迁移或数据身份问题；
- 不在公开仓库、页面、日志或顾客话术中保存个人信息、访问码和凭据；
- 无法执行的测试必须标记为“未验证”，不能写成“已通过”。
